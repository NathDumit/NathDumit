DataOps · orchestration, monitoring and tests

From file to decision: a pipeline that runs by itself and warns you when something changes

The daily flow of an operation that receives files from a legacy system and delivers indicators for decision-making. The examples are invented; the mechanisms are the same as in a real pipeline.

Portfolio project. Every example uses a fictional system and data; no real company, client, system or value appears here. What is real is the method.

The path of the data

Orchestrator

Ordering, retries and lock

Each step declares what it depends on; the orchestrator orders them, retries with increasing backoff on failure, enforces a timeout and uses a lock file so two runs do not collide.

Monitor

Trust, but verify

After the run, it checks that the file exists, is fresh, has the expected rows and columns, and that the volume has not dropped against the median. A process succeeding does not prove the data is right.

Tests

128 tests with synthetic data

Every business rule and every known failure became a test. When the logic changes, the outdated test points to what to touch.

What the first real run taught

1. Initial load

Daily mode only updates what changed; without a full load first, it fails. Now it is an explicit step.

2. Empty variable

An undefined environment variable was passed on as literal text and wrote to the wrong place. Now the run stops before it starts.

3. Hardcoded path

Two scripts ignored the orchestrator and wrote to the default folder. The monitor reported "file missing" and the cause was found.
